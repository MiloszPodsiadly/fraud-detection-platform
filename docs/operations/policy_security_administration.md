# Security, passkeys and institutional trust administration

The Security settings workspace is part of the existing analyst console. It uses the current OIDC session, dedicated `model-policy:credential:*` and `model-policy:trust:*` mandates, and WebAuthn user verification for credential revocation and trust request/review. `FRAUD_OPS_ADMIN` alone has none of these mandates. The backend rechecks identity, scope and independence; hiding a button is not authorization.

## What operators can do

- A credential holder can list their own passkeys and security events, label a passkey, enroll using an independently issued grant, revoke a live passkey with WebAuthn, or use an independently issued lost-device/compromise revocation grant. An administrator cannot list or revoke another actor's passkeys through the holder endpoints.
- Credential grant requests and approvals require different credential administrators; neither may be the target. The short-lived token is returned to the independent approver once and is not stored in plaintext. The holder must transfer it through an approved private channel; it must not go into tickets, chat, logs or repository files.
- A trust requester can propose a structured mandate or public-key change, bound to the current registry generation and digest, the proposed next generation and candidate digest, scope, case reference and a fresh WebAuthn assertion. A different trust approver must step up with their own passkey. Self-review and own-mandate changes are rejected.
- Trust readers see validated public registry metadata, pending requests, decision audit and instance observations. Non-production readers do not see production-scoped entries or requests. No private issuer, publisher or root key is exposed by these APIs.

The request ledger is **not a registry editor**. It cannot write a mounted trust file, generate a root key or activate an approved change. `PENDING_OPERATOR_ACTION` is intentional: an approval authorizes a controlled deployment step, not a live change. A rejected request remains `REJECTED`.

## Protected installation and acknowledgement

Initial root bootstrap and every registry installation remain inside the separately authorized deployment/issuer boundary. For an approved request, the operator must construct the exact full public registry outside the browser, verify that its delta matches the structured request (including identity, key fingerprint, roles, scopes and validity), verify the approved SHA-256 digest, advance the generation and the configured rollback floor, and deploy using the protected read-only mount and isolated publisher key-loader. Restart both alert-service verifiers and the publisher; do not copy private keys into alert-service or the UI. A mismatch or an unavailable verifier is a stop condition, not a reason to relax a check.

Each running alert verifier and publisher reports the generation and canonical digest **loaded in memory** to Mongo. The UI shows up to the latest 100 acknowledgements per registry, the candidate digest, requested generation, and a consistent observed generation/digest only for an approved request when the returned fresh observations agree and both roles are represented. This is not an activation claim: observations are operational evidence, not a cryptographic attestation or a complete deployment inventory; an absent replica cannot acknowledge. A truncated observation set is explicitly marked and cannot establish consistency. The operator must reconcile the actual instance inventory separately. `OBSERVED_CONSISTENT_PENDING_OPERATOR_CONFIRMATION` is deliberately not `COMPLETE`; the ledger stays `PENDING_OPERATOR_ACTION` until a separately authorized deployment-confirmation design is implemented. If the digest, floor or instance inventory cannot be proven, keep the change pending and escalate.

The Operations view reports blocked publication-job count, recent publisher heartbeat, Mongo replica-set transaction capability, OIDC/WebAuthn configuration presence and trust-observation consistency. It evaluates at most the latest 1,000 fresh trust observations; a larger set reports `OBSERVATION_SET_TRUNCATED` instead of a consistency result. `HEARTBEAT_OBSERVED` is not a successful signing probe; `CONFIGURED_NOT_PROBED` is not an OIDC health check. Mongo or observation failures return `UNKNOWN` rather than a false ready state. Production operations diagnostics require both production and trust-read mandates.

The legacy `.local/model-promotion-policy` directory remains ignored by Git. Development bootstrap may create initial public registries and local signing material there. Routine UI actions never modify it. In production the file mounts, key loader, deployment approvals, expected instance inventory and rollback-floor advancement must be controlled and audited by the deployment operator.
