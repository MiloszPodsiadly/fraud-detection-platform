## Partial-deletion protection

The private reader previously validated returned `device_observations` rows against immutable `device_occurrences` rows. Equal but incomplete sets, including loss of both rows, could escape that comparison. Stage A now records a private HMAC commitment and count for the exact historical member set on the current occurrence. Stage B compares bounded observation, occurrence and candidate ID sets in one snapshot and recomputes that anchor; status tampering and any missing representation fail closed. A second fresh snapshot repeats the Device comparison and revalidates the current binding, coverage revision/generation and revocation state. Source and scored authority are checked outside the Device transaction because the two databases do not share a distributed snapshot. The anchor cannot prove source-population completeness and relies on the current occurrence and application integrity key remaining trusted. There is no cached diagnostic result.

Two required occurrence window indexes (`occurrence_device_window`, `occurrence_customer_window`) support the symmetric completeness check; the existing revocation lookup index remains. Exact schema validation rejects an older index set at startup. No `collMod` or index migration was executed. A schema owner must review and apply the additive indexes offline before deploying this version to an existing database; admission remains disabled until that gate is approved.

The observability audit also removed raw transaction, correlation, customer, alert and source-event IDs from structured application logs in the ingest-to-alert path. The request context still supports downstream Kafka header propagation through a scoped thread-local, while `TraceContext` clears those values from MDC for the duration of processing and restores any outer context afterward. The integration canary asserts that transaction, correlation, customer, account, source-event and device identifiers do not appear in captured application logs or metric tags. No trace exporter or alerting service is configured in this repository; external platform-side log/trace transformations are not demonstrated.

## Recovery procedures represented by the code

- For an ambiguous Device Mongo commit, rely on the bounded same-transaction retry and durable reconciliation. If an authorized caller must retry, it must submit the same signed source and Device facts; changed facts conflict. There is no manual “clear unknown” operation.
- For RAW/ENRICHED/SCORED publication uncertainty, restart the existing recovery worker. It reloads the durable intent and republishes the canonical stored event; duplicate delivery is possible and is handled by the existing identity fence. Do not infer failure from a missing producer ACK.
- A terminal DLT/quarantine disposition remains terminal until the existing owner-controlled, bounded redrive path validates the stored intent and current authority. No direct database status update is a supported recovery command.
- Schema mismatch, revoked authority, incomplete coverage or partial deletion requires owner review or source recovery; no automatic DDL, synthesized history, manual membership restore or counter edit is supported.

The repository has no approved production operator CLI, alert routing, retention/erasure runbook or redrive command for Device admission. This document records service behavior rather than inventing production commands. Test commands and injected boundaries are recorded below.
