# Model-policy credential trust and recovery

Policy approval passkeys are bound to the OIDC issuer and subject and verified by the server with Yubico WebAuthn (exact origin and RP ID, fresh one-use challenge, user verification, ownership and signature counter). An OIDC login by itself is never enrollment authority. Client-provided `amr`, `acr`, or an MFA checkbox is not accepted as step-up evidence.

The local Keycloak realm does not currently provide a server-verifiable recent high-assurance authentication timestamp. Enrollment therefore uses an independently approved, short-lived grant. Two *different* OIDC identities in the dedicated `model-policy-credential-admin` group participate: one requests with target issuer, subject, purpose and case reference; the other reviews with an active passkey. Neither may be the target. The review signature binds the request ID, purpose, target issuer/subject, requester, reviewer, case reference, original request expiry, server-planned grant expiry, operation ID and exact APPROVE/REJECT decision. The retained assertion and audit record can be independently reverified. The local fixture contains `policy-security-a` and `policy-security-b` only for development.

For the first administrator, a separate protected installation authority may mount `MODEL_PROMOTION_CREDENTIAL_BOOTSTRAP_PATH`. Its JSON manifest must contain exactly `version` (`policy-credential-bootstrap-v1`), `authorizationId`, `requestId`, `targetIssuer`, `targetSubject`, `requestedBy`, `approvedBy`, `caseReference`, `requestExpiresAt`, `expiresAt`, `installationAuthority` and `independentAuthorizer`. The two installation authorizers must be distinct. The protected file is the first-install trust root: provision it through independently controlled operator change approval, outside Git and the browser. The backend accepts it only for an exact, still-pending `FIRST` grant when neither reviewer nor target has any registered credential history, before the manifest expires. A Mongo unique claim consumes its authorization ID once. With no mounted file, bootstrap fails closed. A revoked administrator credential cannot invoke this first-install path to recover. Remove the manifest after the target has claimed the approved grant; subsequent grants use signed WebAuthn review. This path deliberately relies on protected file custody, not an unverified IdP MFA flag.

Mount this manifest read-only for the service account and keep the installation change record under separate custody. After the requester creates the `FIRST` request, the two installation authorizers verify its exact target, reviewer, case and `requestExpiresAt` through their controlled channel, then provision one manifest for that request. Use a unique `authorizationId`, set `expiresAt` no later than `requestExpiresAt`, and record both authorizers' distinct identities. The application verifies exact fields and one-time use; it cannot independently prove that the out-of-band authorizers performed their organizational approval. Keep the protected change record for audit.

Approval stores a protected authorization record and returns no bearer secret. The target signs in and sees only their own approved grant metadata at `GET /webauthn/enrollment-grants/mine`. `POST /{id}/claim` rechecks the signed proof or protected bootstrap record and returns a fresh 256-bit capability once to that exact issuer/subject. Mongo retains only its SHA-256 digest while the capability is live; consumption clears it transactionally and the scheduled cleanup clears expired digests. A signed grant expires at most 10 minutes after the review challenge starts; a bootstrap grant expires 10 minutes after approval. Registration or protected revocation consumes it in one transaction. The browser keeps it only in memory. A lost HTTP claim response does not reissue a second capability; request a new independent authorization. Grant IDs cannot be enumerated through the target endpoint, and audit/list responses contain no token.

Keycloak imports the fixture when the realm is created; an already-persisted local realm is not silently rewritten. Add the two security-operator users and credential-holder group to an existing local realm through Keycloak administration, or recreate only that local development realm deliberately after preserving needed data.

| Situation | Required proof | Result |
| --- | --- | --- |
| First passkey | `FIRST` grant plus genuine registration ceremony | Active credential with approval provenance |
| Additional passkey | `ADDITIONAL` grant plus genuine registration ceremony | Existing passkey stays active; independent protection is still required |
| Normal revocation | Active passkey assertion bound to target credential and operation | Target permanently revoked |
| Lost device | `LOST_DEVICE_REVOCATION` grant for each inaccessible credential, then `LOST_DEVICE_RECOVERY` grant | Keys become `LOST` and cannot sign; new passkey gets a new identity |
| Suspected compromise | `COMPROMISE_REVOCATION` grant for affected credential, then `COMPROMISE_RECOVERY` grant when no active key remains | Compromised key cannot approve or recover access |

The grant request API is `POST /api/v1/governance/model-policies/webauthn/enrollment-grants`; the independent reviewer inspects `GET /{id}/review`, starts `POST /{id}/review/challenges`, and finishes `POST /{id}/review` with the signed assertion. The exceptional first-install route is `POST /{id}/bootstrap-approval` and requires the exact protected manifest. Restricted auditors can verify signed evidence at `GET /{id}/evidence`. The target sends the claimed `grantToken` to both `POST /webauthn/registrations` and `POST /webauthn/registrations/complete`. Normal revocation uses `POST /webauthn/credentials/{credentialId}/revocation-challenges` followed by `POST /webauthn/credentials/{credentialId}/revoke` with the signed assertion. Protected revocation uses `POST /webauthn/credentials/{credentialId}/protected-revoke` with `grantToken` and `compromised`.

All these paths require a real OIDC session and an explicit credential mandate; grant administration has a separate mandate. Consumed challenges/grants, credential state and append-only security events commit atomically. A duplicate operation or audit insert conflict rolls back the state change. A revoked key is never reactivated, including after service restart. The claim API also rejects approval without a valid retained proof or consumed bootstrap authority. A stolen administrator OIDC session cannot approve a normal grant without its active passkey.

Historical assertion validity and authorization for a **new** decision are separate. The server re-verifies the retained challenge, signed assertion and public key; it also checks the current OIDC actor, publisher and issuer mandates and their configured generation floors. Current signing always requires an active credential. `REVOKED` means routine retirement, `LOST` means inaccessible device, and `COMPROMISED` covers suspected or confirmed compromise. Use the compromise path when the cause is uncertain. Replacing a compromised credential does not restore reliance on an old policy: author and approver must independently review a new policy revision and publish it with current credentials and mandates; the old signed artifact is not rewritten.

| Credential / trust condition | Historical signature integrity | Can credential sign now? | Old policy can authorize a new decision? |
| --- | --- | --- | --- |
| Active; current actor, publisher and issuer mandates | Intact if retained proof verifies | Yes | Yes, if all other policy checks pass |
| Routine retirement (`REVOKED`) | Intact if retained proof verifies | No | Yes, if all current mandates remain valid |
| Lost device (`LOST`) | Intact if retained proof verifies | No | Yes, unless incident response determines compromise |
| Suspected or confirmed compromise (`COMPROMISED`) | Can remain historically intact | No | No; independently approve and issue a new revision |
| Expired/revoked actor mandate or retired/revoked issuer | Can remain historically intact | Depends on credential and actor mandate | No under the current mandate/issuer policy |
| Missing/altered challenge, assertion or public key | Invalid or unavailable | Irrelevant | No |
| Older trust-registry generation than configured floor or retained approval generation | Not a retroactive statement about signature validity | Depends on credential | No; restore current trusted configuration |

Unused expired challenges are removed only after seven days by the scheduled cleanup. Used challenges, assertions, credential public keys and immutable publication proofs have no blanket TTL; retain them for the policy/audit retention period and archive them together before any controlled purge. Removing a referenced challenge or public key makes verification fail closed. A lost HTTP response or process restart does not require a new key for already committed evidence.
