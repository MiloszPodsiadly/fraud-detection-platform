# Model policy governance workflow

The first-party workflow runs inside `alert-service` and uses its existing MongoDB replica set. It is separate from model promotion lifecycle decisions and from the final signed-policy registry. It does **not** sign a policy or return `VERIFIED`.

## HTTP contract

All routes are under `/api/v1/governance/model-policies`. Draft reads and editing accept the configured authenticated OIDC/JWT identity. Credential enrollment and policy submission/review require an OIDC login session plus WebAuthn; a bearer token or demo identity alone cannot perform those ceremonies. The actor is a stable SHA-256 identifier of trusted issuer plus subject, not a request-body user ID or display name. JWT policy access requires a configured, matching issuer URI. The draft input contains `intendedApproverActorId` as an assignment, never as an authorization grant; author, publisher and issuer identities are constructed by the backend. The issuer and publisher bindings currently come from `app.model-policy-governance.*` and must match the deployment's trusted keys.

| Method and path | Required explicit authority | Effect |
| --- | --- | --- |
| `GET /` and `GET /{id}` | `model-policy:read` | Scoped proposal read |
| `GET /{id}/history` | `model-policy:audit:read` | Append-only local history read |
| `POST /drafts` | `model-policy:create` | Create editable draft |
| `PUT /drafts/{id}` | `model-policy:create` | Edit only the author's DRAFT, with `expectedVersion` |
| `POST /webauthn/registrations` and `/webauthn/registrations/complete` | `model-policy:credential:enroll` | Enroll a verified credential for the current OIDC identity |
| `GET /webauthn/credentials` and `DELETE /webauthn/credentials/{credentialId}` | `model-policy:credential:enroll` | List or revoke only the current actor's credentials |
| `POST /{id}/submit/challenges` | `model-policy:submit` | Issue a one-time draft-bound submission challenge |
| `POST /{id}/submit` | `model-policy:submit` | Verify an assertion and commit submission |
| `POST /{id}/review/challenges` | `model-policy:approve` or `model-policy:reject`, matching the decision | Issue an independent review challenge |
| `POST /{id}/review` | Matching review authority | Verify an assertion and commit the decision |
| `POST /{id}/publication-requests` | `model-policy:publish:request` | Persist a pending request only after durable verified approval evidence; no signing here |
| `GET /{id}/publication` | `model-policy:read` | Read the durable job state and current signed-policy verification result |

Each mutation requires a unique `operationId`; retries with the same actor, challenge ID and exact assertion return the original committed response. Conflicting reuse returns HTTP 409. Mutations after creation also require `expectedVersion`. A new challenge needs a new operation ID if the old challenge expires. Production proposals additionally require `model-policy:scope:production` on reads and writes. The policy authorities are mapped only from explicit trusted IdP groups (`app.security.model-policy.group-mapping`), not from `REVIEWER` or `FRAUD_OPS_ADMIN`.

New draft create/edit requests carry each `criteria[].thresholds` value as a **plain decimal JSON string**. The backend converts it to `BigDecimal` without rounding; JSON numbers, signs (including `-0`), exponent notation, commas, empty/non-finite values, more than 34 significant digits or more than 24 fractional places are rejected. Count limits require scale zero. Revision and evidence age are bounded by JavaScript's largest exact integer (9,007,199,254,740,991). These are transport limits, not policy quality targets. Criterion-specific bounds remain authoritative on the server: a rate is at most 1, and positive/count requirements come from the criterion schema. Trailing fractional zeros are retained in the new draft's canonical digest. Proposal reads include `exactThresholds` as string values keyed by criterion and limit; the browser uses them for editing and immutable review preview, because legacy numeric JSON fields can lose digits in JavaScript. The stored draft, published policy format and already signed policies are unchanged. A browser without `exactThresholds` disables signing-sensitive review rather than showing a rounded value.

After a lost mutation response, the browser checks `GET /operations/{operationId}` under the same actor and scope before announcing a commit or allowing a new decision. For WebAuthn decisions, session storage retains only the operation identity, actor and intended status so a refreshed view can resume a read-only check; an uncertain assertion is discarded instead of being queued for retry. If no durable receipt exists yet, the outcome stays explicitly uncertain and the operator checks again. Cancelling the browser ceremony does not submit a decision.

For registration, call the first endpoint, parse its `optionsJson`, run the browser's native `navigator.credentials.create()` ceremony, then send `{ "challengeId": "...", "responseJson": JSON.stringify(credential.toJSON()) }` to the completion endpoint. Submission and review similarly call their `/challenges` endpoint with `{ "operationId": "...", "expectedVersion": 0, "decision": "APPROVE" }` (omit `decision` for submission; use `REJECT` for rejection), run `navigator.credentials.get()` with the returned `optionsJson`, and send `{ "operationId": "...", "challengeId": "...", "responseJson": JSON.stringify(credential.toJSON()) }` to `/submit` or `/review`. The `optionsJson` values are WebAuthn `CredentialsContainer` options; browser code can use `PublicKeyCredential.parseCreationOptionsFromJSON()` or `parseRequestOptionsFromJSON()` on their `publicKey` member. Do not put private keys or assertion JSON in local/session storage. The ceremony is a user action, not automatic approval on login.

## State and persistence

`DRAFT → SUBMITTED → APPROVED | REJECTED`; `APPROVED → PUBLICATION_PENDING → PUBLISHED`. The isolated publisher worker owns the final transition. There is no transition from a final review result back to DRAFT. Amendments require a new policy revision. A failed publication remains pending with a retryable or blocked job, not a fabricated `REJECTED` approval.

The proposal, operation receipt, local history event, challenge consumption, credential counter and assertion evidence are committed in one Mongo transaction. Proposal transitions use a version-and-status compare-and-swap; unique indexes protect policy identity, operation IDs and history sequence. A failed audit insert rolls back the state and receipt. The exact draft and digest remain frozen after submission. An action challenge expires after two minutes and hashes a domain-separated contract containing issuer, subject, actor ID, action/decision (`SUBMITTED`, `APPROVED` or `REJECTED`), operation and challenge IDs, nonce, expiration, proposal ID/version, policy ID/revision, draft SHA-256, institutional scope, environment and intended use. Yubico's verifier checks the RP ID, exact origin, signed challenge, registered public key, credential owner, user-verification flag and signature counter. Revocation and current authority are checked again when accepting the action. The durable evidence contains the public assertion response and its SHA-256 alongside the retained challenge request, so a later auditor has the bytes required to re-verify against the stored public credential. The backend Clock assigns `acceptedAt` when the action is accepted, and that time is persisted with the assertion evidence and decision. The authenticator signs the earlier challenge, **not** the later `acceptedAt`; this is not a raw Ed25519 policy signature or a service attestation.

Credentials store only public COSE keys, user handles, counters, owner issuer/subject and revocation state; private keys remain in authenticators. The local defaults (`localhost`, `http://localhost:4173`) support the analyst console origin when the existing OIDC compose overlay is enabled; plain demo-header authentication cannot enroll, submit or review. Institutional mode requires an explicitly configured, host-compatible HTTPS RP ID/origin through `APP_MODEL_POLICY_WEBAUTHN_RP_ID` and `APP_MODEL_POLICY_WEBAUTHN_ORIGIN`; localhost and loopback origins are rejected for `prod`, `production`, `staging`, and `bank`, or whenever `AUDIT_BANK_MODE_FAIL_CLOSED=true`, regardless of profile name. Existing sessions can retain IdP group grants until refreshed; immediate external IdP revocation requires session invalidation or refreshed authority and must not be claimed as a guarantee of this local workflow. The pending request does not change the signed-policy store or model eligibility until the isolated worker independently verifies retained evidence, signs and commits immutable publication.
