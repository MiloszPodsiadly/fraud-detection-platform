# Model Card publication recovery

Use this procedure only for an interrupted offline Model Card publication. Recovery is operator-controlled and fails closed whenever lock ownership is uncertain.

1. Stop or suspend every scheduled and manually started Model Card publisher for the affected artifact root. Confirm termination through the workload manager and host process inventory. The PID recorded in the lock is supporting evidence only; PID absence or reuse does not prove ownership ended.
2. Record the incident time, deployment or job identity, artifact version, host, operator, lock contents and file metadata, relevant publisher logs, and hashes of any files inspected. Do not follow symlinks while inspecting the artifact root.
3. Inspect the final version directory first. If it exists, do not delete, replace, or republish that version. This includes a `ModelCardPublicationDurabilityUnconfirmed` outcome after a successful rename and failed destination-parent synchronization. Record that durable persistence was not confirmed, validate the visible directory with the canonical Python Model Card reader, and retain its manifest and file hashes. A valid directory is visible published evidence but does not retroactively prove the failed directory synchronization; an invalid or ambiguous directory requires escalation.
4. Read the exact `.<version>.publish.lock` as data and correlate its `ownerToken`, host, PID, and creation time with workload-manager and publisher logs. Age or PID alone is never sufficient. If a publisher may still own the lock, stop and escalate.
5. Inspect only staging directories named `.<version>.staging-*`. Never treat them as published evidence and never move them into the final destination. Remove or quarantine a staging directory only after proving the owning publisher has terminated, the final destination is absent, and the directory belongs to the incident being recovered. Leave unrelated staging directories untouched.
6. After ownership is conclusively cleared and the destination is confirmed absent, remove only the exact stale lock. Rechecking or repeating removal of an already absent stale lock is harmless; encountering a new lock means a publisher started and recovery must stop.
7. Only when the final destination is absent may one fresh publisher be started for the same deterministic input and version. It creates and validates a new staging directory and performs the normal synchronized atomic no-replace publication. Never reuse an interrupted staging directory or bypass the writer. A visible destination after an indeterminate post-rename failure permanently blocks automatic republication of that version.
8. Validate the resulting directory with the canonical reader, retain the incident record, and resume scheduling only after the result is unambiguous.

Hard process termination and storage power loss between filesystem operations cannot be deterministically reproduced in-process. Automated tests inject file and directory synchronization failures and simulate orphaned locks and independently owned staging directories. They prove operation ordering, fail-closed behavior, ownership-safe cleanup, preservation of a destination visible after rename, and version immutability; they do not certify a filesystem, storage controller, or hardware platform against power loss.

## Reader deployment boundary

Provision the host artifact root with controlled ownership before publication; neither the writer nor Compose may create it implicitly. Publish an immutable version directory there using one authorized offline writer identity. After canonical validation, set `MODEL_CARD_ARTIFACT_ROOT` to that host root and `MODEL_CARD_CURRENT_VERSION` to the exact version directory, then apply `deployment/docker-compose.model-card-generated.yml` with the base Compose file. The overlay mounts the complete root read-only into `alert-service` and constructs the canonical JSON path inside that exact version. Do not grant the alert-service container write access, mount a mutable symlink pointer, or run the publisher with the reader identity.
