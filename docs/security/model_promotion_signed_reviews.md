# Signed model-promotion reviews

Production model-promotion APPROVE and REJECT reviews use the existing institutional passkey verifier. The browser obtains a challenge from `POST /api/v1/governance/model-promotion/proposals/{proposalId}/reviews/challenges` using the usual review fields (`approvalId`, `outcome`, `operationId`, `rationale`, `rationaleSha256`). It confirms the WebAuthn assertion and submits `{ "intent": <same review fields>, "challengeId": "...", "responseJson": "..." }` to `POST /reviews/signed`. The old `POST /reviews` remains for non-production scopes but rejects normal production reviews without a signed proof.

If the signed completion response is lost, the browser checks `GET /api/v1/governance/model-promotion/proposals/{proposalId}/reviews/operations/{operationId}`. The read requires the original OIDC reviewer, the current review mandate and environment scope, and a matching committed proposal plus WebAuthn evidence. The UI compares proposal, operation, approval, outcome and rationale digest before reporting success. Until that receipt is available it reports an uncertain result and blocks another decision; checking it never replays the assertion or starts another ceremony. Session storage holds only operation identity, selection, outcome and rationale digest for recovery after refresh. Assertion JSON remains only in the in-flight browser call, never in local/session storage or a retry closure.

Each accepted signed review and trust-registry request/review stores one internal, versioned `governance-bound-webauthn-proof-v1` document. It retains the exact UTF-8 assertion response, server assertion request, canonical domain-separated action contract, issuer/subject, credential identifier and public-key snapshot, RP ID and origin, required presence/verification flags, previous and observed signature counters, expiry and acceptance time. The review/trust receipt references that proof by challenge ID; the proof, credential counter update, decision and audit insert share a Mongo transaction. A failed audit or lifecycle transition rolls them all back. The independent audit verifier checks the original signature and challenge against the immutable snapshot, not the current credential counter. Ordinary HTTP read models contain at most opaque proof IDs and hashes, never the assertion or public key; only code paths requiring `model-policy:audit:read` may invoke historical verification. No application API updates or deletes committed proofs. Mongo is not WORM storage: protect and archive the proof collection with its linked decisions and audit records for the institutional audit-retention period; missing material fails verification closed.

| Credential/trust state | Historical signature integrity | Current institutional trust | Ability to sign a new action |
| --- | --- | --- | --- |
| Active credential and valid mandates | Intact only if retained signature and contract verify | Reassess against current mandates and registry | Yes, subject to fresh challenge and authorization |
| Routinely retired or lost credential | Can remain intact from the retained key and prior counter | Reassess separately; a loss incident may change reliance | No |
| Compromised credential or withdrawn mandate | Can remain cryptographically intact | Not automatically trusted for current decisions | No |
| Missing or modified proof, signature, challenge or governance object | Invalid or unavailable | Fail closed | No conclusion from that proof |

An intact historical signature establishes what was signed at acceptance, not that the signer or policy remains authorized today. The proof's prior counter and key snapshot are used only for historical replay; later counter advances or key rotation do not rewrite the accepted evidence. Trust-registry approval remains pending protected operator deployment and does not activate a trust file by itself.

The challenge is domain-separated from policy decisions and binds the trusted OIDC issuer/subject, operation and proposal IDs, exact model name/version/feature contract/artifact SHA-256, institutional scope, environment, intended use, source and requested target state, expected and current lifecycle revision, proposal/assessment/policy SHA-256, decision, rationale SHA-256, nonce and expiry. Durable promotion actor and replay identity is derived from the verified issuer and subject, never the configured display/login claim; the exact issuer/subject pair is retained with new proposal, approval and decision records. Neither `acceptedAt` nor the later commit timestamp is represented as signed by the authenticator. Both are assigned server-side. The shared Yubico verifier enforces exact RP origin, UV, one-time challenge, owner and counter. Its evidence, counter update, model review, accepted decision, receipt and local audit participate in the same Mongo transaction. A retry with the identical signed assertion recovers the original review; changed actor, intent or assertion fails closed.

Maker/checker separation, current mandate and production scope, fresh policy/evidence and lifecycle revision are still checked by the existing workflow. A model-promotion decision never authorizes deployment by itself. Existing production callers using the unsigned review endpoint must migrate to the two-step OIDC+WebAuthn flow and register a protected passkey first.

Production retirement normally uses the signed WebAuthn review (`NORMAL_SIGNED_RETIREMENT`). If WebAuthn is unavailable, `EMERGENCY_OIDC_HIGH_ASSURANCE` requires two independent OIDC sessions with dedicated requester/authorizer mandates, production scope and a fresh, signed ID-token `auth_time` plus an exact trusted `acr`. Configure `MODEL_PROMOTION_EMERGENCY_TRUSTED_ISSUER` and `MODEL_PROMOTION_EMERGENCY_TRUSTED_ACR` only after the IdP enforces a protected step-up ceremony and assigns that ACR to its verified result. The configured maximum age is at most 300 seconds. Claims from request bodies, arbitrary `amr` values and an unconfigured ACR never establish assurance. The local password-only Keycloak fixture has no trusted emergency ACR, so this emergency mode fails closed until a verified IdP flow is deployed. `PROTECTED_INTERNAL_BREAK_GLASS` is not implemented. A `BREAK_GLASS` rationale never authorizes an unsigned review. Neither `FRAUD_OPS_ADMIN` nor `REVIEWER` grants the dedicated emergency mandates; the model proposer cannot be requester or authorizer.

The requester records the exact pending RETIRED proposal, artifact SHA-256, source state/revision, institution, intended use, approval/review operation IDs, incident ID, evidence reference and specific reason. An independent authorizer inspects the exact intent hash and records a separate rationale. Incident evidence is `INDEPENDENT_HUMAN_ATTESTATION`; an incident ID alone is `INCIDENT_REFERENCE_DECLARED`. The trust-incident subsystem monitors platform trust and does not certify arbitrary model-retirement cases, so this path never claims `AUTHORITATIVE_INTERNAL_INCIDENT_VERIFIED`.

The authorizer approves metadata only. The original requester then calls `POST /emergency-authorizations/{id}/claim` from their own fresh assured session; only that actor receives the single-use 256-bit token. Mongo retains only its SHA-256. The browser immediately submits it with the exact retirement command and never shows it to the authorizer or stores it in browser storage. The durable state is `REQUESTED -> AUTHORIZED -> CLAIMED -> CONSUMED`, or any unconsumed state to `REVOKED`. A lost claim response leaves the grant `CLAIMED`: it cannot issue a second token. Revoke it and create a new independently approved request. Consumption, model transition, champion-claim release, review record and emergency audit commit in one Mongo transaction. The review audit action is `EMERGENCY_RETIRE_MODEL_PROMOTION_PROPOSAL`.

The local OIDC overlay maps `model-promotion-production` to production scope and includes separate requester/authorizer fixture accounts. Existing persisted Keycloak realms are not silently reimported: provision these groups and users explicitly there. This mapping is for the local environment; production IAM must assign distinct operators and govern revocation.

Grants created before the assurance and claim fields were introduced have no verifiable assurance record and fail closed on use. Revoke those outstanding grants and create new exact requests after the trusted IdP flow is configured.

`GET /api/v1/governance/model-promotion/emergency-authorizations/{id}` lets the authorizer inspect intent without a token. `GET /emergency-authorizations/active?actorId=...&incidentId=...` lists at most 100 active grants for incident response; `POST /emergency-authorizations/active/revoke` revokes up to 100 matching grants with CAS and audit in one transaction. Repeat while `hasMore` is true and recheck for grants issued concurrently. A dedicated production auditor reads `/audit`, including incident reference, independent rationale, actors, state and committed-proof status. Grant records and audit events have no TTL and follow institutional retention.

OIDC login, Mongo transactions and a second available operator are required. Current IdP role removal or account disablement does not introspect and revoke an existing application session or Mongo grant. An unexpired stolen session that still carries the dedicated mandate and fresh high-assurance claim can act until the shorter of session invalidation, assurance freshness and the five-minute grant expiry. Incident operators must disable IdP sessions and revoke all affected active grants; the CAS with consumption makes the first committed operation win. An IdP outage prevents new login or step-up, but an existing fresh application session may remain usable; Mongo unavailability prevents grant verification and retirement. This local record is protected human attestation, not external or WORM incident proof.
