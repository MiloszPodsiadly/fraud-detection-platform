# Policy governance workspace

The Policy Governance workspace is separate from Model Promotion. Authors use a structured policy form; the server supplies all required criteria, evidence-source descriptions, threshold keys, units and limit types. New drafts have blank policy limits and evidence ages. The form does not invent observed ML results, PASS evidence, or an approval. Backend validation remains authoritative and the backend's SHA-256 identifies the frozen revision shown for WebAuthn review.

Authors with `model-policy:directory:read` can query `GET /api/v1/governance/model-policies/approvers?environment=...&intendedUse=...`. The response is restricted to active approver mandates matching the selected scope and excludes the caller. It gives a readable configured display name and the stable actor ID stored in the draft. It does not grant roles. The backend checks the chosen approver's current mandate again when accepting a review. If the deployment-owned actor registry lacks a display name, the UI shows a short institutional actor reference; existing local registries are not silently rewritten.

The list uses `GET /api/v1/governance/model-policies/page` with a maximum page size of 50, optional status/policy-ID-prefix filters, and a stable `(updatedAt, id)` cursor. History uses `GET /{id}/history/page` with a maximum page size of 50 and a version cursor. Both preserve production scope and require the existing read/audit mandates. The older list/history endpoints remain for compatibility; the legacy history response is capped at its oldest 200 entries, while the paged endpoint provides access to the complete history. The workspace uses paged endpoints.

Every governance mutation keeps its original operation ID for the live browser session. If an HTTP response is lost, `GET /api/v1/governance/model-policies/operations/{operationId}` returns the caller's durable committed receipt. When no receipt is found, the UI explicitly says the outcome is uncertain and offers a retry of that same command. WebAuthn assertion JSON is held only in memory for that retry; it is not written to localStorage or sessionStorage. Closing the page discards it, so an operator may need to inspect the server-side history before initiating any new logical operation. A 401/403 remains a login/mandate denial, never a claimed commit.

The workspace exposes pending review, exact draft comparison, signed review rationale, publication status, full trust versus signature-only evidence, and bounded audit history. Server permissions determine visibility; hidden controls are not an authorization boundary. Local Keycloak import changes require explicit provisioning in already-persisted realms.
